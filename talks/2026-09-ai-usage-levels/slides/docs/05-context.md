> ซึ่งหักมุขที่สไลด์ 4 เพิ่งสร้างไว้ (ยิ่งเขียนยาวยิ่งดี) โดยตั้งใจ

## บีต 2 — พับ → บิน → คลี่

เวอร์ชันแรกให้กอง `keep` ยุบหายไปเฉยๆ แล้วไฟล์โผล่ขึ้นมาพร้อมเนื้อในทันที
**เสียของ** เพราะคนดูต้องเชื่อเอาเองว่าสองอย่างนี้คือของชิ้นเดียวกัน

ตอนนี้ทำเป็น 4 จังหวะ (`toFile()` + `foldFly()`):

| เวลา | เกิดอะไร |
| --- | --- |
| 0ms | กล่องแชทเลื่อนกลับที่ (`is-wide` ออก, 0.55s) |
| 180ms | **ไฟล์เปล่าโผล่มาก่อน** — มีแค่กรอบกับแถบหัว เนื้อในยังล่องหน |
| 680 / 980 / 1280ms | ย่อหน้าใน `keep` ทีละอัน **พับลงเหลือสูง 7px** แล้วบินข้ามไปฝั่งซ้าย |
| +640ms ต่อชิ้น | ถึงที่แล้ว **คลี่ออก** เป็นบล็อกจริง + แถบหัวไฟล์กะพริบรับหนึ่งที |
| 1980ms | กอง `keep` ยุบปิดหลังชิ้นสุดท้ายออกไปแล้ว |

### การจับคู่ 3 ย่อหน้า → 4 บล็อก

| ย่อหน้าในกอง `keep` | ไปเป็น |
| --- | --- |
| `k-0` ระบบ / repo / log / DB / ทีม | `b-head` + `b-addr` |
| `k-1` ช่วยไล่หาสาเหตุ เทียบข้อมูล อย่าเดา | `b-step` |
| `k-2` ตอบเป็นภาษาธุรกิจก่อน แล้วแยกเป็น... | `b-fmt` |

ตารางนี้อยู่ในตัวแปร `FOLD` **การจับคู่คือส่วนที่ให้ข้อมูล ไม่ใช่แค่ของตกแต่ง** —
มันคือสิ่งที่ทำให้คนดูเข้าใจว่าไฟล์ไม่ใช่ของใหม่ มันคือของเดิมที่ย้ายที่

### ทำไมต้องบินเป็น "ผี"

`foldFly()` **ไม่ได้ย้ายย่อหน้าจริง** แต่ `cloneNode` ไปวางใน `.fly`
(ชั้นลอย `position:absolute; inset:0; z-index:4`) เหตุผลเดียวกับสไลด์ 4:
ย่อหน้าจริงอยู่ในฟองที่ `overflow` ตัดอยู่ ย้ายออกไม่ได้ และปลายทางขนาดไม่เท่าต้นทาง

ผีคือ `<p>` ที่ถูกสวมคลาส `.gh` ทับ (พื้นครีม + เส้นซ้ายสีแดง = หน้าตาของกอง `keep`)
แล้วสั่งสามอย่างพร้อมกัน: `height` → 7px (พับ) · `width` หด · `transform` เลื่อนไปปลายทาง
โดยให้ `transform` หน่วง 0.18s เพื่อให้**พับก่อนแล้วค่อยออกเดินทาง** ไม่ใช่พับไปบินไป

ย่อหน้าต้นทางถูก `visibility: hidden` (ไม่ใช่ `display:none`) เพื่อไม่ให้ย่อหน้า
ที่เหลือขยับระหว่างที่ยังบินกันอยู่

### ท่านี้ต่างจากสไลด์ 4 ยังไง

สไลด์ 4 คือ *ของหลายชิ้นบินมาประกอบกันเป็นฟองเดียว* (translate + cross-fade)
สไลด์ 5 คือ *ของถูกพับเก็บเข้าแฟ้ม* (fold → travel → unfold)
**กลไกเดียวกันแต่คนละท่า** — จงใจไม่ให้ซ้ำ เพราะคนดูเพิ่งเห็นสไลด์ 4 มาหมาดๆ

   ส่วนที่นี่บล็อกในไฟล์กินที่อยู่แล้วตั้งแต่แรก แค่ `opacity: 0` ตำแหน่งเลยนิ่ง)
2. **ต้อง "ปิดงาน" บีตก่อนหน้าให้เรียบร้อยก่อนเล่นบีตถัดไป**
   `setBeat()` เรียก `rebuild(n - 1)` ก่อนรัน `STEP[n]` เสมอ
   เพราะ STEP หลายตัวทยอยเปิดของด้วย `at()` ถ้าคนกดรัวๆ `clearTimers()` จะฆ่า timer
   ที่ยังไม่ทำงาน แล้ว**ไฟล์หรือของบนจอจะหายไปทั้งอัน** (เจอจริงตอนกดถี่ 200ms)
   `rebuild()` วางสถานะแบบไม่มีอนิเมชัน เลยปลอดภัยที่จะเรียกซ้ำ
3. **เนื้อไฟล์ล้นกรอบง่ายมาก** ช่อง `.doc` สูง 358 เนื้อปัจจุบันเต็มพอดี เหลือ 0px
   ตอนเพิ่มบรรทัด `ทีมที่เกี่ยวข้อง` กับฟอร์แมตคำตอบที่ยาวขึ้น ล้นไป 40px
   ต้องไล่บีบทีละอย่าง: `font-size` 12.5→12 · `line-height` 1.45→1.38 ·
   `.ds` margin 8→6 · padding ล่าง 11→4 · ตัดฟอร์แมตคำตอบให้เหลือ 2 บรรทัด
   **จะเติมอะไรอีก ต้องเอาอย่างอื่นออกก่อน** เช็คด้วย `doc.scrollHeight - doc.clientHeight`
4. **กอง `keep` เป็นสีครีม ฟองฝั่งเราก็สีครีม** ครีมทับครีมมองไม่ออก
   ฟองพรอมต์ของบีต 1 เลยต้องมี class `split` ที่ดันพื้นเป็น `--ground-light`
   (`.msg.split .bub`) และกินเต็มความกว้าง — `.msg.you .col` มี `align-items: flex-end`
   อยู่ ต้องสั่ง `width: 100%` ที่ตัว `.bub` เองด้วย ไม่งั้นฟองหดตามเนื้อ
5. **บีต 6 ต้องคงหน้าต่างแชทไว้** แต่ล้าง `.feed` ก่อนใส่ `.case` ใหม่ — ห้ามวาง
   การ์ดทับนอก viewport หรือปล่อยบทสนทนาเก่าให้อ่านปนกับแชทใหม่
6. **`hilite()` ต้องล้างของเดิมก่อนเสมอ** ไม่งั้นชุด `a` กับ `b` จะติดค้างทับกัน
   แล้วมุก "คนละบรรทัด" พัง
7. **`--accent` ใช้จุดเดียว: กอง `keep` ในบีต 1** (เส้นซ้าย + ป้าย) เพราะกองนั้นคือ
   ของที่ทั้งสไลด์กำลังจะพูดถึง — ไฮไลต์ในไฟล์ใช้ครีม `--frame`
8. **บรรทัดคำบรรยายบีต 6 ยาวสองบรรทัด** วัดแล้วขอบล่างอยู่ที่ y 552 ชนขอบฉาก 556 พอดี
9. **Browser pane ชอบส่งเฟรมค้าง** ตอนตรวจงานอย่าเชื่อ screenshot อย่างเดียว
   ให้อ่าน `classList` ผ่าน `javascript_tool` ประกอบด้วย (เจอเหมือนสไลด์ 4)
